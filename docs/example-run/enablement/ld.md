Produce a performance-based curriculum skeleton — objectives, 4-I session design, instructor, assessment, remediation — for field technicians and project engineers adopting AI assistants, held as a design pending pilot and explicitly gated on the Change Management Lead's ADKAR evidence rather than scheduled as a firm calendar.

Body:
There is no evidence yet of Desire or Knowledge at the frontline, only Awareness. If frontline interviews find the real barrier is Desire (fear of role security), training will not fix that, and I will hand it back. What follows is the curriculum to run once that evidence clears — not a commitment to run it now.

**Observable objectives:**
1. Technician: given a flagged work order and the assistant's confidence score, decides act/defer/escalate and logs the reason within the shift. Gradable pass/fail against a rubric. **Provisional**: this assumes the tool exposes an interpretable, calibrated confidence score. That has not been verified against the actual vendor tool — owner: Product/Platform Lead to confirm before this objective is locked.
2. Project engineer: given an AI-drafted scope/estimate deviation, identifies which inputs to check, corrects or overrides the draft, and documents the override rationale.
"Understands how the model works" is deliberately excluded — unassessable, and a Desire lever for Change Management, not a session for me.

**Technician track** (half-day, pilot cohort ~12): Inductive — technicians surface a case where they overrode an automated system OR disagreed with a colleague's judgment call; for anyone without such a case, a short written vignette substitutes so the on-ramp doesn't exclude technicians whose trade never exposed them to override situations. Input — confidence-score meaning, escalation thresholds, logging requirement. Implementation — paired practice on six real flagged work orders (Operations to supply historical cases), including one correct-override case. Integration — first live use in week one, shadowed by the supervisor, against a documentation checklist.

**Project engineer track**: same structure, estimation-deviation cases, cohort ~8. Runs after the technician pilot, same instructor gap below.

**Instructor:** vendor's applications engineer confirmed for session one only. No internal instructor named — one-cohort design unless the firm names an internal SME to co-facilitate session one as train-the-trainer, built into the pilot itself.

**Time release:** 4 hours per technician, 4 hours per engineer, plus unspecified supervisor shadow time — assumption, not commitment; no manager has agreed to it.

**Assessment:** rubric-scored pass/fail on the paired exercise, plus supervisor sign-off on one real logged override in week two. Beyond the pilot window, the technician's direct supervisor reviews override patterns monthly, escalating disputed calls to the Ops Manager, so accountability doesn't end when sustained use begins.

**Remediation:** technicians who don't clear the rubric get one round of supervisor coaching, reassessed in two weeks. No remediation owner exists yet for engineers beyond the one-time vendor session — needs a name before launch.

Durations and cohort sizes are design estimates, loosely informed by comparable frontline AI-tool rollouts; treat as pilot hypotheses, not a schedule.
